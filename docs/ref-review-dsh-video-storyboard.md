## 0. 它和我们是什么关系

同一个哲学，不同的交付物。两家都相信「ffmpeg 零 token 量测 → 少量图给模型看」，所以它的很多结论是在**替我们验证 D1/D2**，而不是替代我们。

| | 它 | 我们 |
|---|---|---|
| 输入 | 本地视频文件 | 视频链接（yt-dlp）／本地文件 |
| 交付物 | **一张可寻址的图版** + 文字清单，交给**别的 agent** 当场读 | `note.md` 成品笔记 + 图片 + 导出三件套 |
| 谁写正文 | 调用方模型（工具只回图和清单） | 我们在 `pipeline/` 里按 `NOTE_CONTRACT` 写 |
| 成本模型 | 1 图 = 384 token，8–16 格 | 1 图 ≈ 346 token（756px 5×5），全片 1 张 + 每段 1 张 |
| 时间轴粒度 | 格（cell），每格带绝对起止时间 | 图版 tile（行/列 → 秒，manifest 为准） |
| 强项 | **格怎么分、帧怎么挑、文字怎么省** | **笔记怎么组织、怎么验收、怎么交付** |

**一句话判断**：它把"看图"这一步做到了工程极限；我们把它当成"看完之后干什么"。所以要借的是**取证决策**，不是产品形态。

## 1. 直接可借（按性价比排序）

### A. 三候选选最清晰帧（Laplacian 方差）★★★ 最推荐先做

**它解决的问题**：一个镜头内取哪一帧。`ffmpeg thumbnail=n=` 按"直方图最接近段均值"挑帧，而**模糊不改变直方图**，所以淡入、失焦、溶解、字幕未定稿的帧会被选中。它实测在同一秒里 `--pick thumb` 给出高斯糊死的片尾字幕，`--pick sharp` 给出清晰帧。

**机制**（`src/sheet.js:297-344`）：每段取 3 个候选（段首+0.25s、中点、段尾−0.25s），三个 ffmpeg 进程**并发**各 seek 解 1 帧，缩到格尺寸后算 Laplacian 方差取最大：

```
灰度 = 0.299R + 0.587G + 0.114B
v = -4·c + 上 + 下 + 左 + 右      # 4 邻域，不含对角，不归一化
方差 = E[v²] - E[v]²
```

**为什么对我们特别值**：我们的痛点就在这——`DECISIONS.md` D5 抓到过 Loading 帧，README 里也写着"图版里的文字一律不采信"。Laplacian 选帧不能解决"抓错内容"，但能解决"抓到内容了但糊"：`still.py` 与 `pipeline/run.py` 的 `extract_still()` 现在只按时刻取一帧，取到过场/淡入就白给。

**落地**：`pipeline/run.py::extract_still()` 上加 `--pick sharp`（3 候选 + 方差比较，约 40 行，纯 Python + numpy 或 PIL 都行）。图版（`vw.py grid`）那层不改（vendor 只读），但**定点截图**这一层是纯收益。
**工作量**：小（半天以内，含对比验证）。

---

### B. 密度积分分格：把「cut / even 二选一」变成一条连续的规则 ★★★

**它解决的问题**：`DECISIONS.md` D12 的困境。我们现在的做法是"按切点分段，最短的一段先并，单段超过 120s 硬劈"——切点密的地方（`BV1Xdnc6jEbL` 426s 里 172 个切点）段会更碎，切点稀的地方（`BV1W3go6tERZ` 264s 只有 2 个）只能靠 `--sections-mode even` 人工兜。

**机制**（`src/density.js`）：给时间轴建一条密度曲线 `density(t) = clamp(局部剪辑率/全片平均剪辑率, 1, 2.5)`，然后在**密度积分上等分**——每段承载的"信息量"相等，快切区自然分到更短的段、更多的格，慢区段变长。边界再吸附到真实切点，但**吸附位移超过理想段长的 30% 就放弃**（否则权重分配被打乱）。

三个细节值得抄：
1. **两遍 + 箱型平滑**：不平滑的话，均匀剪辑的片子会在每个切点附近鼓一个包，识别出一堆假"爆发"。
2. **第三条信号（台词密度）**：说话快的地方也短一点，但只给 0.75–1.4 的温和放大，免得压过画面信号。
3. **配对的 `fitSegments`**（`src/segments.js`）：段数多于目标就**反复合并"合并后最短"的那一对相邻段"**（保护长镜头）；少于目标就**对半拆最长段**，拆到比 `minGap` 还短就停。而且 `minGap` 不是固定 1.2s，而是 `min(1.2, 中位段长 × 0.9)`——不然一条全是 1s 短镜头的片子会被并到凑不够段数（它的实测：6 段被并成 3 段）。

**对我们**：这套能直接替掉 `run.py::plan_sections()` 里的 `merge(20.0)` + `max_span 120` 启发式，且**不需要删掉 `--sections-mode even`**——`even` 仍是无切点素材的兜底，但默认路径会好很多。
**工作量**：中（`segments.py` ~90 行 + `density.py` ~100 行，纯函数、可单测；参考实现有两个现成单测可对照）。

### C. 转写后处理三件套 ★★★ 我们文档记过的病，它都给了药

我们 README 里白纸黑字写着"`base` 模型中文同音错字不少（大理/大概、案号/暗号）"；D11 记录过英文被判成中文、整片乱码。它给了三个**便宜且确定性**的补丁（都在 `src/asr.js`）：

1. **术语替换表**：`~/.dsh/asr.json` 里写 `{"绘插": "彗差"}`，键按**长度降序**、`re.escape` 后拼成**一条交替正则**做单遍替换（防"替换后的文本再被短键命中"），并把"N 处术语已校正"写进清单——**不静默改写**。
   对我们：`BV1EAKH6GE7C` 里 `setter` 被听成"寒暑"、`BV1Xdnc6jEbL` 里"贵是贵点但吃了不烧心"被转错——现在靠人工回原帧核对，有了表就能批量修，且**修了什么可查**。
2. **音乐幻觉过滤**：`dur > 8s && 实义字/秒 < 0.8` → 判为 `music-like` 丢弃，`punctuation-only` 同样丢；被丢的**逐条报告**（`{kept, dropped:[{reason, charsPerSec}]}`）。依据是实测正常口播 2–6 字/秒。
   对我们：纯 BGM 段、片头曲、MV 类素材目前会把幻觉句子写进 `transcript.md`，然后被笔记引用。我们甚至没有这类素材的判据。
3. **"文字落在静音里"计数**：统计"≥60% 时长压在静音段里"的句子数（纯内存判断，不额外跑 ffmpeg）——语义是"轻声被 −40dB 吞了"或"ASR 编字"。这个数应当直接进 `BRIEF.md` 告警。

**工作量**：小（三件加起来 ~120 行，无新依赖）。

### D. 文本预算：每格 120 字、句末截断、可分页 ★★

**它遇到的问题**：2h35m 的片子产生 64 格 + **75 KB** 文字清单，超过宿主工具结果上限，超出部分被折进磁盘文件**而模型不会去读**，于是 44 分钟台词静默消失。

**它的三道闸**（`formatManifest`）：每格 `detail: low/med/high = 60/120/400` 字，且**在句末标点处截断**（在 `[0.5×limit, limit]` 里找最后一个 `。！？；` 再补 `…`）；总量超限时**按格截断**并明确写出续读指令（`[text stopped at cell 13 of 64 — call again with cellRange: [14,64]]`）；`textOnly: true` 只回文字不回图，翻页零 token。

**对我们**：`research.json` 现在是全量 `asr` 数组 + 全部 tile 映射，40 分钟以上的片子会到几百 KB，`BRIEF.md` 又只给"全文见 transcript.md"——写作时其实没有**按格对齐的台词**。两件事可以一起做：给 BRIEF 的每张图版列"第几行第几列 → 秒 → 该秒的台词（截 120 字）"，并对长片加 `--text-page` 分页。
**工作量**：小。

### E. 长片按窗口读：`probe` 0 token → `plan` → 只看窗口 ★★

**它解决的问题**：正是我们 README「已知限制」第一条——**采样盲区**。25 帧覆盖 40 分钟 = 每 96 秒一帧。我们现在的长片（`BV1YV411w72F_p2` 25.6 分钟、`p1` 20 分钟）就吃这个亏：一张 5×5 图版等于看 25 张陌生截图。

**它的策略**（`src/plan.js::planWindows`）：>20 分钟就**别扫全片**；默认 300s 一窗、上限 12 窗；**超上限时拉长窗长而不是砍尾巴**（90 分钟 → 12×450s 覆盖全片，而不是 12×300s 只到 60 分钟）；尾窗 <30s 并入前一窗（不为 2 秒的窗口花一整张图的 token）；窗口边界**吸附到真实切点**（吸附后不得短于 span×30%，否则放弃）；`--plan` 只打印窗口表，**0 token**。

对我们的形态就是：`run.py <url> --windows 300` 产出 `w01..wNN` 图版 + 一张 `windows.md` 时间表，BRIEF 里直接给出"先看哪 2–3 窗"的建议（**这个开关后来被否决，见下方注**）。**这比提高 5×5 的格子数更省**（每多一张 384 token，比 25 格变 36 格便宜不了，但覆盖到了细节）。

> **后来被否决**（2026-10-28，见 `docs/plan-windows.md` §1 与 `DECISIONS.md` D16）：固定像素预算下
> "帧数×每格面积≈常数"，4×4 每格像素 −43%；且 5/8 段横跨两窗、破坏"每章一张图"的契约。
> 实做改成"长片章节自动等分 + 按段长给格数 + `zoom.py` 按需密集图版"。`--windows` 这个开关未实现、已删除。
>
> **工作量**：小（当时的预估偏高）。

### F. 下一个真正的信号：响度 + 字/秒 ★★

**它的发现**（`docs/BASELINE.md` 实测四支片）：**响度与语速反向**——最吵的片子说得最少。

| 素材 | 平均响度 | 字/秒 | 判型 |
|---|---|---|---|
| 口播教程 | −23.0 LUFS | **5.59** | speech |
| 叙事动画 | −21.4 LUFS | 2.05 | narrative |
| 概念 PV | **−14.2 LUFS** | 0.16 | **music** |
| 官方 PV | −18.4 LUFS | 0.75 | near-music |

判据只有一行：`meanLufs > -18 && charsPerSec < 1` → 音乐驱动，于是"格数地板"抬到 9（信息全在画面上）；反过来 `字/秒 > 3` 就把格数 ×0.6（台词承担信息，图只做锚点）。

**对我们**：D8 的体例分叉现在只看"冻结帧 ≥5 / 关键词 ≥2"，是一条**纯画面**判据。加上"是不是音乐驱动 / 是不是纯口播"这一维，可以顺手解决两件事：① `--style auto` 更稳；② **纯 MV 素材直接告警"这篇不该按教程/学习笔记写"**（我们目前会硬写出一篇空洞笔记）。
**成本**：`ebur128` 一条滤镜，2 小时片子约几十秒；字/秒我们已经有了（`asr` 段全在手上）。
**工作量**：小。

### G. 零碎但便宜的东西

| 项 | 它怎么做 | 对我们的用处 |
|---|---|---|
| 扫描结果缓存 | 键 = `sha1(input|size|mtime|窗口|阈值)`，命中后同片二次调用 13.4s → 3.6s | 我们 `run.py` 重跑要重新 probe + 重新出全部图版；加一层 `probe`/`sections` 缓存能省掉大部分 |
| `-ss` 放在 `-i` 前 | 输入侧 seek，切片快且时间基准明确 | 我们 `extract_still()` 已是这种写法，保持 |
| 空格不编号、灰底横杠 | 空位绝不烧编号，避免"把 padding 当内容" | 我们图版不满格时（`vw.py` 会跳过取不到的帧）会出现无编号空格，规则可对齐 |
| 徽标高度 15% 格高 | 66×37 下采样后仍可读；11% 是极限 | 我们 `drawtext` 字号 `tile_w//8`（5×5 时 149px 格宽 → 18px 字 + 黑底黄字），量级相当，无需改 |
| 封面裁切 `scale=...:increase,crop` | 等比铺满再居中裁，绝不变形 | `vw.py` 用 `scale=tile_w:-2`，不裁切——留黑边比变形好，保持现状 |
| 每格带 `cuts 7` | 格内切点数 + 全片平均间距 | 写作时能判断"这段是不是快剪"，很便宜，可加进 manifest |

## 2. 不建议照搬（附我们的实测）

### ✗ HSV + 「按速率反推阈值」不能直接用在录屏语料上

它最强的卖点是切分器（`src/scan.js`）：64×36 HSV 三通道差、阈值按"约 1 刀 / 1.5s"反推、floor 12，声称同一支片子 `scdet` 召回 4/9 而它 9/9。

我在**我们自己的 4 支素材**上复现了它的算法（`work/refs/hsv_scan.py`，Python + numpy，逻辑逐行对齐），和 `vw.py` 现在用的 `scdet=t=10` 对比：

| 素材 | 时长 | scdet 切点 | HSV 切点 | HSV 阈值 | 抽帧人工判定 |
|---|---|---|---|---|---|
| `BV1EAKH6GE7C` 教程 | 593s | 69 | **151** | 13 | scdet 的 69 个**全部**被 HSV 覆盖；多出的 82 个**抽查 4 个全是真转场**（换游戏、切 UI 场景）|
| `BV1W3go6tERZ` 演示 | 264s | 2 | 30 | 12 | 5 个抽查：3 真（标题卡、换构图、换 take）／2 假（只是角色在动）|
| `BV1YV411w72F_p2` 讲座录屏 | 1537s | **0** | **154** | 12 | 抽查 4 个**全是鼠标/选中高亮**，一个真转场都没有 |
| `BV1uf8e6dEyA` 短片 | 113s | 3 | 20 | 19 | 未抽查 |

读法：
- **`scdet` 的固定阈值是真问题**：教程片多出的 82 个里，我抽帧确认的 4 个（582.2 / 309.4 / 443.0 / 292.1s，含"换游戏"和"切 UI 场景"）**它一个都没找到**，其中最强的 HSV 分 82.8。这一条它说对了。
- **但它的速率阈值在录屏上会灾难性过检**：1537s 的讲座，`p50=0.2 / p90=1.2 / p99=10.0`——**整片几乎没有画面变化**，它却因为"目标 1 刀/1.5s"这条配额，在 p99 之上又切了 154 刀，全是 3D 视口里的高亮块和鼠标轨迹。它的实测素材全是 B-roll／动画／PV，**没有一支是录屏**，所以这条经验不覆盖我们的主力语料。

**结论**：要借的是「HSV 打分本身」（62× 实时，比 scdet 快、且对同亮度换色不瞎），**不是**那条"按速率定阈值"。落到我们这里应该是：
1. 先把 `scdet` 换成 HSV 打分（保留分数序列，不只留切点）；
2. 阈值按**素材类型**分档——`content_kind` 判为"低运动屏幕录制"时用高分位（如 p99.5 且绝对值 ≥25），判为"剪辑类"时用它的速率法；
3. 切点只当**候选章节边界**，不当"镜头"（这一点 D12 已经用血换过一次）。

### ✗ 单图 384 token 的"一图哲学"不是新东西
它把 9–16 帧塞进 1 张 ≈640k 像素（384 token）；我们是 25 帧塞进 756×756（≈346 token）。**我们是更省的**，不必改。它真正的贡献是"**让模型早停**"（`probe` 0 token、`--plan` 0 token、`textOnly` 翻页），那是编排问题，不是拼图问题（见 E/D）。

### ✗ 自绘像素、不用图像库
它用 `Buffer` 手写 PNG/点阵字体，为了"零依赖 + 不在陌生机器上崩字体"。我们有 ImageMagick + ffmpeg 的 `drawtext` 且已跑通，改成手绘没有收益（`vw.py` 的 `montage` 反而更省事）。

### ✗ 音频条（同轴响度图）
对**交互式看图**很有用（"第 5 格落在副歌前的安静段"）。我们是**离线写笔记**，读者看的是成品 md，不是那张图；把响度画进图版只增加渲染复杂度。但**测量**那部分（响度/静音/起音）值得单独接进来当判型信号（见 F）。

### ✗ Node/DSH 插件形态
我们是 Python 管道 + 交付物；它是 DSH 工具 + 即时查询。形态不同，不迁移。

## 3. 抄的时候别抄错的地方

它的代码里有几处**注释与实现不一致**（已核对）：

| 位置 | 文档/注释说 | 代码实际 |
|---|---|---|
| `burn: 'index+time'` | 会把时间码烧进画面 | 只判 `burn !== 'none'`，**时间码从未画**（等于 `index`）|
| 音频条高度 | 受格高 40% 约束 | 实际 `0.28` |
| 起音阈值 | `6 / 12 dB` | 实现与 README 是 `8 / 15 dB` |
| 徽标 | "不透明优先" | `alpha = 0.85` |
| `withCache(enabled)` | 可开关缓存 | 参数**未被解构**，靠 `key=null` 短路 |
| `pruneCache` | LRU | 读不刷新 mtime，实为**写入时间 FIFO**，热窗口可能被挤掉 |
| `validatePlan` / `planTotal` | 有规划护栏 | DSH 工具路径**从未调用**，只在库/CLI/测试生效 |
| `endEdge()` | 处理片尾边界 | 只有测试在用，管线靠 `duration − 0.2` 夹住 |

单测是它的加分项（154 个，含 ffmpeg e2e 与"拿宿主真 `defineTool` 编译 schema"的契约测试）——**契约测试这个思路我们也可以有**：`note_audit.py` 目前验的是成品笔记，缺一个"`run.py` 产出的 `research.json`/`BRIEF.md` 结构自检"。

## 4. 如果只做三件事

| 顺序 | 做什么 | 为什么是它 | 工作量 |
|---|---|---|---|
| 1 | **Laplacian 三选一选帧**（A） | 直接提升图版/截图的"可读性"，D5 的痛（抓到过场/糊帧）少一半，改动局限在 `extract_still()` | 半天 |
| 2 | **转写后处理三件套**（C） | 直接治 README 里写着的同音错字，且"改了什么"可查；无新依赖 | 1 天 |
| 3 | **切分决策层**：HSV 打分 + 分类型阈值（§2 的修正版）+ 密度积分分格（B） | 替掉 `plan_sections()` 的 20s/120s 启发式，D12 的 `even` 从"唯一出路"降级为"兜底" | 2–3 天 |

再往后：`--windows` 长片模式（E）→ 响度+字/秒判型（F）→ 图版 manifest 加 `cuts` 与逐格台词（D/G）。

### 附：参考仓库跑不起来的说明
`node bin/scan-video.mjs` 在本沙箱里直接 `spawn EPERM`——Node 的 `child_process` 默认管道被拒（和 `git clone` 的 `Permission denied` 同源）。**Python 侧同样拿不到管道**（`subprocess` 的 `CreatePipe` 报 `WinError 5`），所以两个复现脚本都改成"子进程输出落文件、读文件"（`run_no_pipe()` / `call()`），这条只影响由 agent 在本会话里起的进程，不影响你手工跑 `pipeline/run.py`。

因此它的实现我**没有端到端跑通**，只读了代码并把算法搬到 Python 里对比；上面所有数字都来自我们自己的复现，不是抄它的 README。
